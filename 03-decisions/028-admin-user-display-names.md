# ADR-028: 관리자 응답에 사용자·처리자의 현재 이름 제공

- 상태: 제안 — Codex 작성, 담당자 문서 확인 전
- 작성자 / 날짜: Codex / 2026-10-21
- 검토자: 사용자가 표시 방식·문서 반영을 승인했으며 ADR 문서 자체 검토는 대기
- 관련 작업 기록 / PR: [관리자 응답 이름 계약 정리](../04-worklogs/2026-10-21-admin-user-display-names.md) / 코드 PR 없음
- 대체 범위: 일부 관리자 응답의 ID 전용 표시와 관리자 개별 알림 수신자 이름의 제외 범위를 보완한다. 기존 업무·개인정보 공개 규칙 전체를 대체하지 않는다.

## 배경

관리자 추첨 결과에서 UUID만 보여 테스트 사용자의 당첨·재추첨 전후 동일인 여부를 알아보기 어려웠다. 전체 관리자 응답을 검토한 결과 대상 사용자뿐 아니라 취소·검증·실행·발표 처리자와 미션·출석 정책 작성자도 ID만 제공하는 응답이 확인됐다.

## 결정과 이유

- 변경 전: 일부 관리자 응답에 사용자·관리자 ID만 있었다.
- 변경 후: 기존 ID를 유지하고 그 ID에 해당하는 현재 사용자 이름을 표시용으로 함께 제공한다. 공통 의미는 [공통 API 계약](../05-api/common.md#관리자-응답의-사용자처리자-이름), 필드 위치·타입은 각 API 명세를 원본으로 한다.
- 이름이 바뀌어도 기존 ID로 동일인을 식별할 수 있으므로 작업 당시 이름을 새로 저장하지 않는다. 현재 사용자 정보의 `name`을 사용하며 별도 닉네임 정책을 도입하지 않는다.
- 원본 추첨 근거·확정 결과·과거 감사 기록을 변경하지 않는다. 현재 이름이 달라졌다는 이유로 재선정·새 공개·새 업무 처리를 생성하지 않는다.

## 검토한 대안

ID만 유지하는 방식과 기존 ID 옆에 현재 이름을 제공하는 방식을 비교했다. 작업 당시 이름을 별도로 보관하는 차이도 설명했으며 사용자는 기존 ID로 작업자를 추적할 수 있으므로 현재 이름 제공이면 충분하다고 확인했다. 성능 실험이나 코드 변경은 수행하지 않았다.

## 영향과 범위

- 관리자 계약: [추첨](../05-api/drawing.md#2026-10-21-관리자-이름-표시-계약), [응모](../05-api/entry.md#2026-10-21-관리자-사용자-이름-추가), [알림](../05-api/notification.md#2026-10-21-관리자-알림-수신자-이름-추가), [응모권](../05-api/ticket.md#2026-10-21-관리자-정합성-조회-사용자-이름-추가), [미션](../05-api/mission.md#2026-10-21-관리자-미션-작성자-이름-추가), [출석](../05-api/attendance.md#2026-10-21-관리자-출석-정책-작성자-이름-추가)의 지정한 DTO만 확장한다.
- 프론트엔드는 이름으로 사용자를 알아보고 ID로 동일인·동명이인을 구분한다. nullable ID에 대응하는 이름의 null 처리와 추가 필드 검증을 반영해야 한다.
- 백엔드는 기존 사용자 정보와 연결해 응답을 보완한다. 조회 쿼리·DTO 변환·테스트 등 구현 세부는 백엔드 저장소에서 관리한다. DB 컬럼 추가나 마이그레이션은 이번 결정의 작업 범위가 아니다.
- 일반 사용자 공개 당첨자의 기존 마스킹, 설문 자유 서술의 익명성, 알림 작업의 전체 수신자 명단 제외를 유지한다. 알림 작업 내부 처리 위치에는 이름을 추가하지 않는다.
- 문서의 계약 확정과 코드 구현·테스트·리뷰·배포 완료를 구분한다. 이 문서 작업으로 다른 담당자의 코드를 수정하거나 작업 완료로 처리하지 않는다.
